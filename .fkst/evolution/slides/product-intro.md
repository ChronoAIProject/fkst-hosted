## The problem with delegating implementation

You hand off a task. Then you lose the thread.

- What is actually running right now?
- Is it healthy, or quietly stuck?
- What did it produce, and against which commit?
- If the service goes down, is any of that recoverable?

## One loop, driven entirely by GitHub issues

**Open a trigger issue** → a session starts
**Open a labelled work issue** → the session works it
**The session opens a pull request** → you review it

Sessions are started, driven, and stopped through GitHub issues. There is no
second control surface to learn.

## GitHub is the only durable record

The control plane keeps **no database**.

Queues, caches and leases are process-local. Lose all of them and nothing is
lost: state is reconstructed from issues, labels, pull requests and releases.

Your source never lives here. It lives in your repository.

<!--
Evidence: protected fact `github-is-the-only-durable-store` and the

## Who may do what

| Role | May |
| --- | --- |
| **Effective creator** | Drive their own session; author its work |
| **Session Collaborator** | Author work on that session |
| **Global administrator** | Both, deployment-wide |

Repository admin or maintain permission alone is **not** work authority.

## What this does not promise

- A session produces **candidate** pull requests for human review. No outcome is
  guaranteed.
- fkst-hosted contains **no kernel-engine code** — that lives upstream in
  `fkst-substrate`.
- It is not a CI system, an issue tracker, or a replacement for code review.
